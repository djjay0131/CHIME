\begin{abstract}
CHIME~\cite{chime2024} is a hybrid B$+$~tree/hopscotch index for RDMA-attached disaggregated memory whose five compile-time-toggled features --- hopscotch leaf nodes, vacancy-aware locks, metadata replication, sibling-based validation, and speculative reads --- are calibrated against RDMA's $\sim$2\,$\mu$s round-trip cost. This report reproduces CHIME on CloudLab r650 hardware and ports it to CXL-attached memory via a single \texttt{USE\_CXL} compile flag, then asks how the feature stack transfers across an order-of-magnitude latency change.

Three runtime findings emerge. First, CHIME-CXL reproduces across days and across seven distinct physical r650 nodes within $\sim 3$--$5\%$, while CHIME-RDMA varies by up to $\sim 2\times$ on the same hardware class --- making CXL the more stable benchmark target on shared testbeds. Second, CHIME's speculative-read optimization is net-negative on CXL: full CHIME-CXL is $17\%$ slower than the same code with that one flag disabled, dropping it below the no-features Sherman-CXL baseline ($\sim 66\sigma$ across $n=20$ reps). Third, on range scans Sherman-CXL beats full CHIME-CXL by $1.4$--$1.7\times$, indicating that the RDMA-targeted feature stack is net overhead on synchronous CXL.

Two methodological contributions accompany the runtime results. A one-line allocator overlap (\texttt{CxlTransport::alloc\_offset\_} overwriting \texttt{root\_ptr\_ptr} at offset 8\,MB) was the root cause of a CXL crash that haunted three reservations and was fixed by reserving the first 16\,MB. We also document a six-day CloudLab reservation-scheduler outage (April 22--26) with full UUID timeline, verbatim error strings, and three concrete portal API additions, each independently sufficient to surface root cause inside the first failed window. The artifact is open-source at \url{https://github.com/djjay0131/CHIME}.
\end{abstract}

\section{Introduction and Project Scope}
\label{sec:intro}
%% Spec §1; rubric guidelines: scope-setting for the rest of the report.
%% ============================================================

This work has two halves: a reproduction of CHIME's~\cite{chime2024} RDMA-based throughput-latency and ablation results on commodity academic hardware, and a port of CHIME from RDMA to CXL-attached memory for a transport-comparison study. Both halves are accompanied by an independent stress-testing finding on Sherman's LOAD-phase behavior.

The reproduction half produced paper-matching trends on five YCSB workloads across five competing methods (CHIME, Sherman, SMART, ROLEX, SMART-SC) on CloudLab's r650 cluster at Clemson. The CXL-port half produced a complete, reproducible code port (a single \texttt{USE\_CXL=ON} flag swaps the entire transport layer), an automated build-verification environment in Docker, an automated smoke gate, a debug-artifact-capture harness, and a single-point cache-consumption surrogate --- all unit-tested off-hardware. None of those produced runtime measurements, because four CloudLab reservations between April 22 and April 26 were not honored by the experiment scheduler. We document this outage in detail and treat it as a finding in its own right.

The Sherman stress-testing finding (§\ref{sec:stress}) is independent of the CXL story: under the same r650 setup, Sherman's LOAD phase crashes deterministically at moderate scale on an assertion (\texttt{Tree.cpp:382}) that has no escape hatch for the borrow/merge race that produces it. CHIME's \texttt{SIBLING\_BASED\_VALIDATION} and \texttt{VACANCY\_AWARE\_LOCK} flags close that window. The crash empirically reinforces the paper's claim that CHIME's techniques are jointly necessary, not merely a throughput stack.

\paragraph{Reading guide.} §\ref{sec:setup} distinguishes the paper's experimental setup from ours. §\ref{sec:approach} describes the agent-orchestrated experimentation pipeline used throughout, and contrasts it with ORNL's multi-agent HPC-facility work~\cite{ornl-agents-xloop25}. §\ref{sec:effort} catalogs engineering obstacles. §\ref{sec:repro} presents the reproduction results. §\ref{sec:stress} presents the Sherman LOAD-crash stress-testing finding. §\ref{sec:cxl-engineering} describes the CXL-port engineering. §\ref{sec:postmortem} reports the CXL runtime evaluation, the cross-day and cross-hardware reproducibility findings, and the postmortem of the reservation outage encountered along the way. §\ref{sec:conclusion} concludes.

\section{Experimental Setup: Paper vs. Actual}
\label{sec:setup}
%% Spec §2; rubric guideline #1.
%% ============================================================


Following the instructor's guideline \#1, this section distinguishes the experimental setup described in the CHIME paper~\cite{chime2024} from the setup we actually used on CloudLab, and discusses the effects of the differences on our results.

\subsection{Paper's Setup}

The CHIME paper evaluates on an 11-node cluster: 10 compute nodes (CN) and 1 memory node (MN). Each node is a server-class machine with two Intel Xeon sockets and Mellanox ConnectX NICs running InfiniBand at 100\,Gbps with the MLNX OFED userspace stack. Workloads are drawn from YCSB~\cite{ycsb}: workloads A, B, C, D, E, and a LOAD phase that pre-populates the index. Key sizes are 8\,B, value sizes are 8\,B, and the dataset scales to 100~M keys for the throughput-latency figures and 40--120~M keys for the cache-consumption figure (Fig.\,14). Each CN runs 64 client threads.

\subsection{Our Setup on CloudLab}

We ran on CloudLab's r650 cluster at Clemson. r650 nodes match the paper's expected hardware class --- dual-socket Intel Xeon Gold 6338N, 256\,GB DDR4, two NUMA domains --- but with two important differences: the network fabric is Ethernet running RoCE~v2 rather than native InfiniBand, and CloudLab's hardware availability constrained our experiments to fewer compute nodes than the paper used. Our two completed runs were:

\begin{itemize}[nosep]
    \item \textbf{Run~7} (April 5--6, 2026, 16h experiment): 6$\times$r650 with 5 CN + 1 MN. Produced fig\_15a, fig\_15b, fig\_12 workloads C and D.
    \item \textbf{Run~8} (April 6--7, 2026, 20h experiment with extension): 4$\times$r650 with 3 CN + 1 MN. Produced fig\_12 workload E and partial LOAD; fig\_12 A was completed on the cluster but not pulled before reservation expiry, and fig\_12 B is partial (CHIME 5 of 8 thread points).
\end{itemize}

A pre-deadline dry run (March 23--26) used 11$\times$r6525 nodes (AMD EPYC, ConnectX-5/6 Dx) at Clemson because r650 capacity was unavailable; this run validated our harness end-to-end but is not a paper-matched data point. Software stack: Ubuntu 20.04, GCC 9, CMake 3.10, MLNX OFED 5.6, YCSB 0.17.0. Workloads: paper-matched A/B/C/D/E/LOAD; key and value sizes match the paper.

\subsection{Differences and Their Effects}

\begin{itemize}[nosep,leftmargin=1em]
    \item \textbf{Compute-node count: 5 (Run~7) and 3 (Run~8), versus the paper's 10.} Total throughput numbers are absolute and do not directly compare with the paper. The shape of the throughput-versus-thread-count curves is preserved, however, because per-CN behavior is independent of CN count up to the point where the MN saturates. Trends carry; absolute peaks do not.
    \item \textbf{Network: RoCE~v2 over Ethernet, versus the paper's native InfiniBand.} RoCE adds approximately 0.5\,$\mu$s of latency per operation relative to IB. The effect on the throughput-latency curves is a uniform rightward shift; relative ordering between methods is preserved. Two of the six RoCE-specific source fixes (\S\ref{sec:effort-roce}) are required just to get any RDMA traffic flowing on r650 Clemson, which is itself an artifact-availability finding.
    \item \textbf{Hardware variant for the dry run: r6525 (AMD EPYC) instead of r650 (Intel Xeon).} r6525 has 64 physical cores per node versus r650's 72; different cache hierarchy and memory-bandwidth characteristics. We do not draw comparisons with the paper from the r6525 run; it served as harness validation and as a source of the RoCE fixes that later carried over to r650.
    \item \textbf{Workload scale.} The paper's Fig.\,14 sweeps cache consumption over 40--120\,M keys. We did not regenerate the larger workloads in time for the RDMA reproduction runs and so did not attempt Fig.\,14 directly. The CXL-port specification calls for a single-point surrogate at 60\,M keys (\S\ref{sec:cxl-fig14}) which would have addressed the trend question with one ablation rather than four.
\end{itemize}

\section{Approach: Agent-Orchestrated Experimentation Pipeline}
\label{sec:approach}
%% Spec llm/features/final-project-reframe.md §3; rubric guideline #2.
%% ============================================================

A reproduction-and-port study at the scope of this project --- five competing methods, two transports (RDMA and CXL), two CN-count configurations, four reproducible workloads, on a shared academic testbed with sub-day reservation windows and a six-day scheduler outage in the middle --- is more orchestration than research. We organized the work as an agent-orchestrated pipeline of three coupled layers: (i) a persona-driven user workflow, where each Claude session is invoked in one of a small set of roles with persistent memory and feature-spec substrates that survive session boundaries; (ii) a programmatic CloudLab control surface that wraps the testbed's XML-RPC and web-portal APIs; (iii) an autonomous cluster-side runner that executes a multi-phase experiment plan on the cluster without a human in the loop, waking the laptop-side agent only on a 29-minute cadence to pull results, regenerate plots, and commit. This section names each layer with its in-tree artifacts, then names what the pipeline got us and where it broke. The negative-result findings --- a control-plane gap that requires interactive web-UI access (which an agent cannot drive), and the scheduler-binding outage that no agent could diagnose without a working \texttt{reservationStatus} RPC --- map to the three concrete CloudLab API additions reported in §\ref{sec:postmortem} and re-stated as primary contributions in §\ref{sec:approach:cloudlab}.

\subsection{Persona-Driven User Workflow}
\label{sec:approach:fleet}

The work uses a persona-driven workflow in which each Claude session is invoked in one of six roles --- not a self-orchestrating agent fleet, but a substrate of roles, persistent memory, and feature specs that survives session boundaries and project pivots. Almost every commit is a human-invoked Claude Code session; an autonomous self-handoff loop is future work. The contribution we claim here is the substrate, not the autonomy.

\paragraph{Personas.} Six personas are defined in \texttt{.claude/agents/}: \emph{feature-architect} (specifying features), \emph{construction-lead} (implementing them), \emph{knowledge-steward} (memory-bank maintenance), \emph{memory-agent} (administrative memory updates), \emph{construction-agent} (sprint and phase coordination), and \emph{proposal-agent} (LaTeX writing carried over from a prior project). Each persona has a defined identity, working style, and skill set; the human invokes one per task. The separation of roles is what prevents a single Claude session from carrying the full project context --- a workload that exceeds Claude's context window and produces incoherent output by the third or fourth pivot.

\paragraph{Persistent memory.} The substrate keeps a small persistent store that any persona reads at the start of a session and updates at the end --- enough to carry project context across sessions without re-deriving it from the codebase each time. Alongside the memory, \texttt{llm/features/} contains the project's feature specifications: \texttt{cxl-implementation.md}, \texttt{final-project.md} (the original Apr 21 plan), \texttt{final-project-no-hardware.md} (the Apr 27 postmortem-pivot when four reservations failed), and \texttt{final-project-reframe.md} (this report's own May 3 reframe). The four-spec sequence is the most concrete evidence that the substrate held up: each spec was authored when the project's reality changed, the prior spec was not deleted, and downstream personas could read the chain to understand what was promised, what was delivered, and why the scope shifted. The memory format and update protocol are an implementation detail not covered here.

\paragraph{Skills and procedures.} The workflow exposes a small set of skills under \texttt{.claude/skills/} for the recurring procedures the personas run: feature specification, implementation, verification, and memory upkeep. Each skill encodes a phased procedure; the persona executes the phases. This is the closest the workflow gets to autonomy: the procedure is fixed, the persona's judgment fills in the per-phase details, and the human approves the output of each phase before the next begins.

\paragraph{What this layer is not.} It is not an autonomous research agent. It does not generate hypotheses unsupervised, it does not run experiments without explicit human invocation, and it does not produce productivity numbers we can defend. We have no controlled human-only baseline; any claim of "agents made me 3$\times$ faster" would be unsupported. What we can claim is that the substrate stayed coherent across three reality pivots and an order-of-magnitude scope change, which is more than a single-session Claude conversation could have delivered.

\subsection{Programmatic CloudLab Control Surface}
\label{sec:approach:cloudlab}

The second layer wraps CloudLab's two control planes as a programmatic surface usable by an agent. The wrapping is partially successful and partially blocked --- and the blocks are exactly what produced the six-day scheduler outage in §\ref{sec:postmortem}. We describe both halves so the reader sees what an agent on CloudLab can and cannot do today.

\paragraph{The two control planes.} CloudLab exposes two authentication surfaces. The \emph{XML-RPC API} on \texttt{boss.emulab.net:43794} authenticates with a PEM client certificate; this is what the \texttt{portal-tools} CLI uses, and what an agent can drive programmatically (\texttt{createReservation}, \texttt{startExperiment}, \texttt{experimentStatus}, \texttt{experimentManifests}). The \emph{web portal} at \texttt{www.cloudlab.us} authenticates with a JWT cookie; this is the surface required for any \texttt{resgroup.php} or \texttt{list-resgroup.php} page that lets a human inspect reservation state. The two surfaces do not interoperate: a PEM cert against \texttt{www.cloudlab.us} returns an empty response (the web layer ignores cert auth); a JWT against the boss XML-RPC endpoint returns 404 (the RPC layer ignores cookies). For an agent without an interactive browser, the JWT side is structurally inaccessible. We document this asymmetry in §\ref{sec:postmortem}.

\paragraph{What we built on the XML-RPC side.} \texttt{script/cloudlab-setup.py} wraps reservation creation, experiment start, and result pulldown as Python functions. \texttt{script/cloudlab-status-watch.sh} polls the portal API for experiment lifecycle state without falling back to ssh-tail polling (which had previously triggered a CloudLab admin email about ``unusual control-net traffic''). \texttt{script/prep-experiment.sh} runs idempotent post-provision setup on the master node: hugepage allocation to NUMA node 1 (\S\ref{sec:effort-cxl} documents why the default split breaks CXL), memcached.conf with both IP and port lines (the missing port line cost ten hours on Run~7), and the seven-fix RoCE configuration sequence. These three scripts together cover the steady-state lifecycle: claim a reservation, provision an experiment, set up the cluster, run workloads, pull results.

\paragraph{What broke.} Inspecting reservation state requires the \texttt{reservationStatus} RPC, which during the affected period returned a Perl runtime error (\texttt{Undefined subroutine \&main::DoStatus called at /usr/testbed/bin/manage\_resgroup line 208}) regardless of UUID, regardless of authentication mode, regardless of CLI invocation pattern. With \texttt{reservationStatus} broken, the only path to read reservation state was the web UI behind JWT --- the surface an agent cannot drive. The full evidence (server-side bug verbatim, auth-asymmetry table, four-window timeline) is in §\ref{sec:postmortem}.

\paragraph{Three CloudLab API additions, each individually sufficient.}
\label{api-additions:approach}
The following three concrete API additions, copied here from §\ref{api-additions:postmortem} as the contribution-slot punch line, would each independently have surfaced the root cause of the six-day outage inside the first failed reservation window. We re-state them here because they are the contribution this layer claims:
\begin{enumerate}[nosep,leftmargin=*]
    \item \textbf{Fix \texttt{reservationStatus}.} The server-side \texttt{Undefined subroutine \&main::DoStatus} error at \texttt{/usr/testbed/bin/manage\_resgroup} line 208 is a one-line Perl bug. Restoring this RPC restores the only programmatic path to inspect reservation state.
    \item \textbf{Make the scheduler error precise.} The current message ``0 available because of existing resource reservations to other projects or users'' is misleading when capacity is held by the same project but in an unmatched binding. Naming the conflicting reservation UUID, or distinguishing ``no matching reservation'' from ``capacity exhausted by other projects,'' would point at the project/cluster/hardware-type-mismatch hypothesis on first failure.
    \item \textbf{Add \texttt{startExperiment --reservation <uuid>}.} The current reservation-to-experiment binding is implicit (matching project, cluster, hardware-type, time window). An explicit binding flag would let the scheduler return ``your reservation has hardware type $X$ but the profile asks for $Y$'' on the spot.
\end{enumerate}
These three are not editorial complaints. They are testable engineering changes, each individually sufficient to have surfaced the root cause inside the first failed window.

\subsection{Autonomous Cluster-Side Runner}
\label{sec:approach:runner}

The third layer of the pipeline is an autonomous cluster-side runner that executes a multi-phase experiment plan without a human in the loop. The May 2 24-hour sprint is the canonical example: nine phases, twenty-four hours of wall-clock work, the laptop-side agent waking on a 29-minute cadence to pull results and commit. This section names the runner's anatomy.

\paragraph{Phase plan.} The sprint is laid out in \texttt{construction/sprints/sprint-may2-24h.md} as nine numbered phases, each with a UTC time window, a one-line goal, and a pass-fail gate. Phase~0 is provisioning and smoke (RDMA + CXL); Phases~1--2 collect the CHIME/SMART/Sherman/ROLEX RDMA matrix at 3\,CN+1\,MN; Phase~3 measures CXL variance across five replications; Phase~4 is the human-in-loop CXL-port engineering for sibling methods; Phases~5--6 sweep CXL competitor methods and high-thread-count points; Phases~7--8 retry workloads A/B and run a 30-replication variance study; Phase~9 is the final pulldown, plotting, and commit. The phase boundaries are deliberate: each gate either passes (advance) or fails (skip and log), so a single phase failure does not block the rest of the 24-hour sprint.

\paragraph{Cluster-side runner.} \texttt{script/autonomous-runner.sh} (275 lines) drives the phase plan from the master node. Each phase invokes \texttt{ycsb\_test} via a guarded wrapper, redirects all output to NFS at \texttt{/proj/cs620426sp-PG0/djjay-results/may2-24h/}, and updates a heartbeat file every 60 seconds. \texttt{exp/resilient\_runner.py} (394 lines) wraps individual workload runs with checkpoint resume, so a single point that fails or hangs does not lose the whole sweep --- the next sweep iteration starts from where the previous left off. Together the two scripts give the cluster a 24-hour autonomy budget: the master node will finish whatever phases it can finish, write its progress to NFS, and stay alive until either Phase~9 completes or the reservation expires.

\paragraph{Guard rails.} Two guard scripts wrap the runner. \texttt{script/control-net-guard.sh} samples interface byte counters every 30 seconds and aborts the experiment if RDMA traffic appears on the control NIC --- the policy that would otherwise quarantine the experiment, as happened on an early RDMA run. \texttt{script/run-with-guard.sh} wraps each \texttt{ycsb\_test} invocation with the guard plus a per-process OOM watchdog. The two guards together enforce the invariants that previously cost reservation windows to human error: data plane never on the control net, and one OOM never wedges the entire phase.

\paragraph{Laptop-side agent.} A laptop-side agent wakes on a 29-minute cadence (under the cache-window threshold to keep the prompt cache warm) and performs three actions: pull the latest \texttt{exp/results/may2-24h/} from NFS via \texttt{scp -r}, regenerate finding-specific plots locally (\texttt{exp/plot\_competitor\_comparison.py}, \texttt{exp/plot\_transport\_method.py}, \texttt{exp/plot\_cxl\_reproducibility.py}, \texttt{exp/plot\_cxl\_ablation.py}), and commit the new figures and data to \texttt{main}. Crucially, the laptop-side agent does \emph{not} ssh-tail logs --- the previous polling pattern triggered a CloudLab admin email, and the cadenced \texttt{scp} replaced it. The cluster-side runner is the source of truth; the laptop-side agent is a pull-not-push observer.

\subsection{What This Approach Got Us, and What It Did Not}
\label{sec:approach:limits}

\paragraph{What it got us.} The pipeline produced multi-method runtime data on a hard deadline (May 5/May 6) without a tenured-research-staff infrastructure. The May~2 24-hour sprint executed nine phases without a human in the chair beyond Phase~4's CXL-port engineering work. The May~1 single-line allocator fix that unlocked the CXL data path was found because the resilient runner wrote a precise crash trace into NFS that the laptop-side agent could analyze offline (\S\ref{sec:cxl-engineering}). The structured postmortem of the four-window scheduler outage in §\ref{sec:postmortem} is, we think, the project's most reusable artifact: every reservation UUID, every experiment UUID, the verbatim Perl error string, and the reproduction recipe across experiment boundaries are all there.

\paragraph{What it did not get us.} The pipeline did not bridge CloudLab's PEM/JWT auth-layer asymmetry. It did not diagnose the scheduler-binding root cause without a working \texttt{reservationStatus}. It did not replace the human in irreversible decisions: every reservation request, every \texttt{git push --force}, every quarantine-triage call still went through a human. And it did not produce controlled productivity measurements: we have no human-only baseline, so any quantitative claim about agent leverage would be unsupported.

\paragraph{Differentiation from ORNL's XLOOP '25 work.}
The closest published prior art to this approach is Rosendo et al.'s ``AI Agents for Enabling Autonomous Experiments at ORNL's HPC and Manufacturing User Facilities''~\cite{ornl-agents-xloop25}, presented at XLOOP '25 (collocated with SC '25). The ORNL paper describes a multi-agent framework with a natural-language interface, programmable facility APIs, and provenance-aware infrastructure for cross-facility scientific experimentation. Our work overlaps with theirs on three of the four claims of this section: persona-style agents, a programmatic facility control surface, and an autonomous experiment runner. Three points of differentiation make this work a useful complement rather than a duplicate. \emph{Target testbed:} the ORNL paper targets internal HPC and manufacturing user facilities with controlled provenance infrastructure designed by facility operators; this work targets CloudLab/Emulab, the academic community's primary \emph{shared} systems testbed, where the control surface is what users get rather than what facility operators design --- and where the gaps in the surface (\S\ref{sec:approach:cloudlab}) are themselves the contribution. \emph{Operator scale:} ORNL describes institutional infrastructure with facility staff in the loop; this work is a single PhD student on a course timeline with no operator privileges, which constrains what the pipeline can do and makes those constraints generalizable to other student-scale users. \emph{Framing:} ORNL is a success-story paper demonstrating capability; this work is a negative-result analysis whose contribution is the three concrete API additions inferred from where the agent approach broke. The three differentiations are not orthogonal --- a shared testbed, a single-PhD operator, and an outage-driven framing form one consistent story --- but each one independently distinguishes this work from the ORNL line of inquiry.

\paragraph{Forward pointer.} The three CloudLab API additions in §\ref{sec:approach:cloudlab} (and re-detailed in §\ref{sec:postmortem-resstatus}) are the gap. They are named in the contributions block (\S\ref{contrib:orch:2}) because closing them would let the next academic-shared-testbed agent project reach a higher fraction of completion than this one did.

\section{Engineering Effort and Obstacles}
\label{sec:effort}
%% Spec §3; rubric guideline #2.
%% ============================================================


CHIME's published artifact is written assuming the same hardware and software stack the authors used: r650-class Intel Xeon nodes with Mellanox ConnectX-6 NICs running MLNX OFED userspace, paper-validated InfiniBand fabrics, and the authors' YCSB workload regeneration scripts. Every difference between that stack and what CloudLab actually provisions translates into source code edits or operational workarounds. This section catalogs the obstacles we hit and what was required to clear each one. We organize them in roughly the order they were encountered: RoCE on r650 first, then build-system surprises, then the largest single obstacle (reservation reliability) which has its own §\ref{sec:postmortem}.

\subsection{RoCE Configuration on r650 Clemson}
\label{sec:effort-roce}

The r650 nodes at Clemson expose Mellanox ConnectX-6 NICs but \emph{only} over an Ethernet fabric, requiring RoCE v2 instead of native InfiniBand. CHIME's defaults assume IB. Six source-level fixes were required, all sed-applied to \texttt{include/Common.h}, \texttt{include/Rdma.h}, and \texttt{src/rdma/Resource.cpp} on every node before each build:

\begin{enumerate}[nosep]
    \item \texttt{IB\_DEV\_NAME\_IDX = '2'} so the RDMA stack picks \texttt{mlx5\_2} on \texttt{ens2f0} (the VLAN parent NIC), not \texttt{mlx5\_0} on \texttt{eno12399} (the control-net NIC).
    \item \texttt{IBV\_MTU\_1024} (replacing the default IB MTU) because RoCE requires the smaller frame size.
    \item \texttt{MLX\_GID = 3} to select the RoCE v2 GID index attached to the VLAN interface (GID 1 is the link-local address on \texttt{ens2f0} and is not routable).
    \item \texttt{attr->grh.hop\_limit = 64} on every QP attribute --- required for RoCE routing across the cluster's Ethernet fabric.
    \item \texttt{CPU\_PHYSICAL\_CORE\_NUM = 72} to match r650's two-socket 36-core layout (the default of 64 lefts threads pinned to nonexistent cores).
    \item Manual VLAN activation: \texttt{sudo /usr/local/etc/emulab/rc/rc.ifconfig} on every node after boot, because CloudLab assigns VLAN IDs in the profile but does not bring the interface up.
\end{enumerate}

These fixes are idempotent and order-independent, so we automated them into Phase 4 of \texttt{construction/scripts/setup-r650.sh}. Identifying them was a different matter: the first three were discovered by reading verbose \texttt{ibv\_devinfo} output and manually correlating GID/MTU values against RoCE v2 specifications, the fourth came from comparing kernel netlink traces of failed and successful QP transitions, and the fifth was a sentinel-value bug we caught only after instrumenting \texttt{Tree.cpp} to log thread affinity. Total time-on-cluster spent isolating these: approximately two reservation cycles.

\subsection{Internal LAN and the Quarantine Risk}

A subtler hazard, also worth ~10 hours of debugging, is that running RDMA traffic on the CloudLab control network triggers an automated quarantine: the experiment is forcibly terminated and the user receives a network-violation notice. CloudLab profiles must explicitly request an internal LAN. Our profile (\texttt{chime-r650-clemson-lan}) defines an isolated VLAN on \texttt{ens2f0} with \texttt{10.10.1.x/24} addressing baked into \texttt{/etc/hosts}; the public control network on \texttt{eno12399} is reserved for SSH and \texttt{memcached} cluster discovery. This separation is a hard requirement, not a suggestion --- ignoring it is what produced the first three terminated experiments early in the project.

\subsection{The memcached.conf Bug (Approximately 10 Hours Lost)}

On Run 7 (April 5--6, 6$\times$r650, 16h experiment) we lost roughly ten hours of cluster time to a two-line configuration file: \texttt{memcached.conf} requires both an IP line and an explicit port line, but the default examples in CHIME's \texttt{script/restartMemc.sh} ship with the port commented out. Without the port line, \texttt{memcached} starts but binds only to localhost; cluster nodes cannot register, the harness hangs in node discovery, and \texttt{ycsb\_test} eventually fails with no useful diagnostic. The bug was found by running \texttt{ss -tlpn} on the memcached node and noticing the missing 11211 listener. Our fix is a two-line addition in \texttt{script/restartMemc.sh} that writes both lines unconditionally; we now check the file on every node bring-up.

\subsection{YCSB Workload Generation: Python 2 versus Python 3}

YCSB 0.17.0 (the version paired with CHIME's harness) ships with Python 2 syntax for its workload generator: \texttt{except subprocess.CalledProcessError, err} as the canonical pattern, and a runtime mix of \texttt{bytes} and \texttt{str} that only works under Python 2. CloudLab's r650 image still has Python 2 available; our local Mac and our Docker preflight do not. We attempted three remediation paths in sequence:

\begin{enumerate}[nosep]
    \item Run \texttt{2to3 -w -n} at Docker build time (\texttt{Dockerfile.ycsb-gen}). This handled the syntax errors but left the \texttt{TypeError: a bytes-like object is required} cascade across a dozen string-concatenation sites in the workload-emission path.
    \item Hand-edit the offending sites. Each edit revealed another two; the patch series grew without converging.
    \item Defer regeneration to the cluster, where Python 2 is preinstalled. This is what we actually shipped --- workload generation runs at cluster bring-up using YCSB's stock Python 2 path, costs roughly 20 minutes of reservation time, and produces deterministic output we can pin via SHA-256.
\end{enumerate}

The cost of this detour was about three hours of local debugging that ended in a deferral. The lesson, which we recorded as a feedback memory, is that Py2-shipped tools should be run in a Py2 environment rather than ported.

\subsection{The CXL Build: Five Blockers Beyond the Initial Port}
\label{sec:effort-cxl}

The initial CXL transport implementation (commit \texttt{152b4e9}) compiled in our local IDE but failed in clean-room reproduction. We caught this with a Docker preflight (\texttt{Dockerfile.cxl-preflight}, Ubuntu 20.04 amd64) that builds CHIME-with-\texttt{USE\_CXL=ON} from a fresh clone. Five blockers surfaced; commit \texttt{e430d8d} closes all of them:

\begin{enumerate}[nosep]
    \item \texttt{include/Common.h} used \texttt{std::array} without \texttt{\#include <array>}. Local headers transitively included it; clean-room did not.
    \item The \texttt{CoroPull} stub gated by \texttt{\#ifdef USE\_CXL} omitted \texttt{get()} and \texttt{operator()}, so the call sites in \texttt{Tree.cpp} that consume coroutine results failed to link.
    \item \texttt{getIP()} in \texttt{src/Common.cpp} referenced \texttt{NET\_DEV\_NAME} from \texttt{include/Rdma.h}, which is excluded from the CXL build. Replaced the symbol with a local \texttt{constexpr}.
    \item \texttt{Tree::run\_coroutine} and \texttt{coro\_worker} declared boost coroutine types unconditionally; under \texttt{USE\_CXL} the boost dependencies are dropped from the link line. Wrapped the type usages in \texttt{\#ifndef USE\_CXL}.
    \item \texttt{src/CxlDSM.cpp} omitted \texttt{\#include "Key.h"} and the file built only when other translation units happened to include \texttt{Key.h} earlier in the unit's transitive closure.
\end{enumerate}

Two operational lessons fell out of this. First, \emph{a clean-room build environment is non-negotiable for any port that gates source files via macros}; transitive header inclusion in IDEs masks real failures. Second, \emph{the Docker preflight should be run on every commit}, not just at release time --- four of the five blockers above were one-line fixes that would have surfaced in two minutes of CI had we wired this earlier.

\subsection{The Largest Obstacle: Hardware Reservation Reliability}
\label{sec:effort-reservations}

The single largest obstacle to this project was not a code bug. Across April 22--26 we held four CloudLab r650 reservations against project \texttt{CS620426SP} totaling more than 80 hours of approved capacity. Every \texttt{startExperiment} call against an active reservation returned the same scheduler error and zero nodes were ever provisioned. We have detailed the timeline, the verbatim error, the broken \texttt{reservationStatus} CLI, and the authentication-layer asymmetry that prevented us from diagnosing the issue, in §\ref{sec:postmortem}. The point we make here, in the engineering-effort section, is that the obstacle was real: the same week we shipped a clean Docker preflight, an automated debug-capture harness, a unit-tested cache-consumption surrogate, an automated CXL smoke gate, and a written runbook, we could not get one node to provision. Engineering effort and infrastructure access are different gates; clearing the first does not clear the second.

\section{Stress-Testing Finding: Sherman LOAD Crash}
\label{sec:stress}
%% Spec §5; rubric guidelines #3, #5.
%% ============================================================


Reproduction is one of two halves of this project. The other half --- following the instructor's guideline \#5 --- is to attempt to break the index, observe how it degrades or fails, and reason about why. Our stress testing focused on the workload mix most likely to expose concurrency hazards: high-fan-in writes during the LOAD phase. The headline finding is that Sherman, run with its CHIME-disabled baseline configuration, crashes deterministically at moderate scale on r650; CHIME does not. We treat this as a finding about Sherman's baseline behavior, not as a defect to fix in the comparison.

\subsection{What We Stressed and How}

We pushed the LOAD phase --- the most write-heavy and contention-sensitive part of the YCSB suite --- to its full per-CN concurrency. Run 8 (April 6--7, 3 CN + 1 MN on r650 Clemson) ran each method through the standard 64-threads-per-CN configuration. CHIME, SMART, ROLEX, and SMART-SC completed LOAD; Sherman did not.

\subsection{Sherman LOAD Crash on RDMA}
\label{sec:stress-sherman-crash}

After approximately 5\,M keys loaded, Sherman crashed reproducibly with the following assertion:

\begin{lstlisting}
Assertion `k >= fence_keys.lowest' failed
\end{lstlisting}

The crash site is \texttt{src/Tree.cpp:382} and is preceded in the log by \texttt{RDMA Work Request Flushed} errors on multiple CN threads --- consistent with the hypothesis that a stuck thread is the proximate trigger and the assertion is the structural reason the process cannot recover. Reproduction recipe: 3 CN $\times$ 64 threads, randint distribution, LOAD workload, \texttt{ycsb\_test 3 64 1 randint LOAD} on a fresh tree.

\subsection{Static Analysis: The Fence-Key Invariant}
\label{sec:stress-static-analysis}

We performed off-cluster static analysis of the surrounding code (no live debug session, since the cluster time was reserved for reproduction work). Listing~\ref{lst:tree-382} reproduces the relevant slice.

\begin{lstlisting}[caption={\texttt{src/Tree.cpp}, lines 372--385: the assertion site at 382 has escape hatches for cache-staleness and for $k \ge \mathrm{highest}$, but \emph{not} for $k < \mathrm{lowest}$ on a non-cached read.},label={lst:tree-382}]
const auto& fence_keys = node->metadata.fence_keys;
if (from_cache && (!node->metadata.valid ||
                   k < fence_keys.lowest || k >= fence_keys.highest)) {
  return false;    // escape hatch: retry via cache refresh
}
if (k >= fence_keys.highest) {          // escape hatch: walk right sibling
  node_addr = node->metadata.sibling_ptr;
  path_stack[sink ? sink->get() : 0][level - 1] = node_addr;
  internal_node_search(node_addr, sibling_addr, k, level, false, sink);
  return true;
}
assert(k >= fence_keys.lowest);          // crash site (382)
\end{lstlisting}

The assertion at line 382 is reachable under the following sequence. Thread A, performing a borrow or merge that grows N's \emph{lower} fence key, updates \texttt{N.fence\_keys.lowest} in place before the parent pointer is updated. Concurrent thread B descends through a stale parent pointer carrying a key \texttt{k < new\_lowest}. The escape on line 373 fires only \texttt{from\_cache}; the escape on line 376 only handles $k \ge \mathrm{highest}$. The fall-through is the assertion. The dual case (split, where the upper fence shrinks) does \emph{not} trigger the assertion, because line 376 walks the sibling pointer correctly --- this is why some Sherman load runs complete and others crash, depending on which mutation (split versus borrow/merge) occurs during the contention window.

\subsection{Why CHIME Does Not Crash}
\label{sec:stress-why-chime}

Three of CHIME's compile-time features close the window the Sherman baseline leaves open:

\begin{itemize}[nosep]
    \item \texttt{SIBLING\_BASED\_VALIDATION} cross-validates every read of a non-root internal node against the sibling's fence keys. A descent that would land on a node with widened bounds is caught at validation time and retried via re-read.
    \item \texttt{VACANCY\_AWARE\_LOCK} piggybacks the vacancy bitmap on the lock word, forcing readers to see a consistent snapshot of \emph{both} the lock state and the fence keys. The split between ``read fence keys'' and ``read sibling pointer'' that exposes the racy borrow is collapsed.
    \item \texttt{METADATA\_REPLICATION} replicates leaf metadata across segments with version numbers; a stale read on any single segment is detected by mismatched versions before it can advance into the assertion path.
\end{itemize}

These three flags are part of CHIME's \texttt{include/Common.h} and are toggled \emph{off} for the Sherman-equivalent fig\_15a baseline. With them off, the Sherman crash reproduces in CHIME too --- a fact that strengthens the finding rather than weakens it.

\subsection{What This Tells Us}

The crash is not a bug to be patched. It is the empirical version of a claim CHIME's paper makes implicitly: the techniques are jointly necessary for correctness under contention, not merely a throughput optimization stacked on a working baseline. The Sherman baseline reproduces the failure mode on r650; the fix --- adopting \texttt{SIBLING\_BASED\_VALIDATION} or its equivalent --- is essentially what CHIME does. Two minimal patches would close the window in Sherman directly (replace the assertion with a retry loop matching \texttt{decode\_node\_versions} at lines 369--371, or adopt validation as a baseline), but applying either inside the comparison would erase the ablation's central data point. Keeping Sherman's baseline behavior visible \emph{is} the point of fig\_15a.

We did not collect a fig\_12 LOAD data point for Sherman because of this crash. The plot in §\ref{sec:repro} marks Sherman's LOAD entry as crashed; the missing data point is more informative than an artificially completed run would have been.

\section{CXL Port: Engineering}
\label{sec:cxl-engineering}
%% Spec §6; rubric guideline #2 (engineering effort, continued).
%% ============================================================


This section describes the engineering work that was completed for the CXL port. None of it depends on a successful runtime evaluation: the code builds, the harness is unit-tested, the smoke gate is automated, and the artifact reproduces from a fresh clone via Docker. What is missing --- runtime measurements on r650 --- is the subject of §\ref{sec:postmortem}.

\subsection{Why a CXL Port?}

CHIME, like its predecessors, is built around the assumption that the unit operation is an RDMA verb: a one-sided READ, WRITE, or compare-and-swap that traverses the host CPU, the local NIC, the network, and a remote NIC, with completion polled from a completion queue. Each operation costs roughly two microseconds. Many of CHIME's published optimizations --- read batching, speculative reads, vacancy-aware locks, sibling-based validation --- are calibrated against that latency. CXL.mem changes the unit cost: load and store instructions to a CXL-attached memory device cost on the order of 200 nanoseconds, an order of magnitude lower.

That order-of-magnitude shift makes CHIME on CXL an interesting target for two reasons. First, the per-technique value of CHIME's optimizations may shift: some that exist to amortize the cost of a verb may matter less; others, like cache-aware leaf packing, may matter more. Second, the synchronous load/store interface eliminates the coroutine-based async model entirely --- making the port partially a deletion exercise rather than a translation exercise.

\subsection{Architecture: \texttt{CxlTransport} and \texttt{CxlDSM}}
\label{sec:cxl-arch}

We introduce a thin transport abstraction (\texttt{include/CxlTransport.h}, \texttt{src/CxlTransport.cpp}) with the same operation surface as CHIME's existing DSM layer: \texttt{read\_sync}, \texttt{write\_sync}, \texttt{cas\_sync}, \texttt{faa\_boundary\_sync}, \texttt{read\_dm\_sync}, \texttt{barrier}, \texttt{alloc}, and \texttt{free}. Above it, \texttt{CxlDSM} (\texttt{include/CxlDSM.h}, \texttt{src/CxlDSM.cpp}) presents the same public API as the existing \texttt{DSM} class. A preprocessor alias --- \texttt{\#define DSM CxlDSM} --- inside an \texttt{\#ifdef USE\_CXL} block in \texttt{include/DSM.h} swaps the implementation without touching \texttt{Tree.cpp} or \texttt{ycsb\_test.cpp}. The result is a single-flag port: \texttt{cmake -DUSE\_CXL=ON ..} switches the entire transport, and the index code is unchanged.

The transport interface intentionally drops two pieces of RDMA's machinery. First, coroutine-style asynchrony: every CXL operation is a memory load or store, so completion is implicit and the coroutine return-yield-resume harness becomes dead weight. Second, key registration (lkey/rkey) and queue-pair state: a CXL pointer is just a pointer. \texttt{OpRegion}, the transport-agnostic replacement for \texttt{RdmaOpRegion}, contains only \texttt{source}, \texttt{dest} (a \texttt{GlobalAddress}), and \texttt{size}.

\subsection{NUMA Emulation as a Stand-In for CXL}

CloudLab's r650 nodes do not have CXL devices. They are dual-socket Intel Xeon servers with two NUMA domains separated by Intel UPI, which presents the right shape of memory (load/store-coherent, low-latency, separately addressable) at the wrong absolute latency (UPI is closer to 80\,ns; CXL is 200--300\,ns). Following the precedent of TPP and Pond, we emulate CXL by binding execution threads to NUMA node 0 and binding the index's data region to NUMA node 1 via \texttt{mmap} with \texttt{MPOL\_BIND}. Memory semantics match real CXL --- coherent, addressable, no protocol-credit accounting in our path --- but the absolute numbers are an underestimate of CXL's true overhead. The report would have stated this explicitly in any reported figure; in the absence of figures, we state it here as a design caveat.

\subsection{Build-System Surgery}

The mechanical work to thread the \texttt{USE\_CXL} flag through the project, gate the RDMA-only translation units out of the link line, and stub out the boost-coroutine call sites is documented in detail in §\ref{sec:effort-cxl}. The shorthand summary: five blockers between the initial CXL transport implementation (commit \texttt{152b4e9}) and a clean Docker preflight (commit \texttt{e430d8d}), each fixed independently. Once those landed, \texttt{docker build --platform linux/amd64 -f Dockerfile.cxl-preflight -t chime .} followed by \texttt{cmake -DUSE\_CXL=ON \&\& make -j} produces the \texttt{ycsb\_test} binary on a clean machine. This is AC-7 of the project specification, and it is the single piece of the CXL evaluation that survived the hardware outage intact.

\subsection{The Smoke Gate}

The first thing a successful reservation would have run is the CXL smoke gate (\texttt{construction/scripts/smoke-gate.sh}), a two-stage automated check designed to surface a CXL runtime failure within 60 seconds:

\begin{itemize}[nosep]
    \item \textbf{Stage~(a) write-heavy micro-check:} 5\,s of YCSB LOAD inserting 10\,k keys. This exercises CAS-via-\texttt{\_\_sync\_val\_compare\_and\_swap}, the \texttt{alloc} path, and the on-chip-memory routing for lock words. Pass condition: no assertion failure, no segmentation fault.
    \item \textbf{Stage~(b) read-heavy micro-check:} 30\,s of YCSB workload C against the LOAD'd dataset. This exercises read batching, speculative reads, and the cache. Pass condition: throughput $> 0$~ops/s, standard latency histogram in stdout.
\end{itemize}

Both stages must pass before the script returns 0. A failure of either pivots the runbook to RDMA reproduction closure (collect missing \texttt{fig\_12\_a}/\texttt{b} via RDMA) rather than burning the rest of the window on debugging. We chose this two-stage form deliberately: a read-only check would not exercise CHIME's CAS-and-allocation path, which is where the most CXL-specific code lives.

\subsection{Cache Consumption: A Design-Time Discussion}
\label{sec:cxl-fig14}

The original spec called for a \texttt{fig\_14} cache-consumption surrogate (AC-13): a single-point measurement at 60\,M keys --- short of the paper's 40--120\,M sweep --- using the existing \texttt{statistics()} hook in \texttt{src/Tree.cpp} that reports per-CN internal-node cache size. The driver (\texttt{exp/fig\_14\_surrogate.py}) is implemented and unit-tested. The measurement was not run.

What the surrogate would have shown, given the index design, is straightforward to reason about. CHIME's hopscotch leaves pack more keys per leaf than Sherman's B+ leaves at the same per-leaf size, which translates directly into fewer internal-node entries cached per million keys --- the cache-efficiency claim that motivates the paper. SMART's adaptive radix tree pays a different price: variable-width nodes consume less cache than B+ leaves on dense key distributions and more on sparse ones. ROLEX's learned index is dominated by model parameters and is roughly transport-independent.

The CXL transport changes none of this. Cache consumption is a function of the index structure, not the transport. What CXL \emph{does} change is the per-miss penalty: a cache miss that triggers a remote internal-node fetch costs $\sim$200\,ns on CXL versus $\sim$2\,$\mu$s on RDMA, so the marginal value of additional cache shrinks by an order of magnitude. The interesting downstream question --- whether the cache-eviction logic in \texttt{ENABLE\_CACHE\_EVICTION} is still load-bearing on CXL --- requires a runtime measurement we did not get to take. We flag it in §\ref{sec:conclusion} as the most informative single experiment a successor reservation should run.

\subsection{The Diagnostic Dead End: \texttt{reservationStatus}}
\label{sec:postmortem-resstatus}

The standard CloudLab CLI for inspecting a reservation is \texttt{reservationStatus <uuid>}, which calls the XML-RPC method \texttt{portal.reservationStatus} on \texttt{boss.emulab.net:43794}. Throughout the affected period this method returned a Perl runtime error from the server:

\begin{lstlisting}
$ reservationStatus 5565ec96-3ebe-11f1-a92d-c4cbe1eff744
Undefined subroutine &main::DoStatus called at
/usr/testbed/bin/manage_resgroup line 208.
\end{lstlisting}

This is a server-side bug. We confirmed it appears regardless of UUID, regardless of authentication mode, and regardless of CLI invocation pattern --- the call never reaches a working code path. This single bug eliminated the only programmatic route to diagnose the project-mismatch hypothesis below: with a working \texttt{reservationStatus}, we could have read the cluster, hardware-type URN, and project of each reservation and compared them to the profile bindings. Without it, every diagnostic path required interactive web-UI access.

\subsection{Authentication-Layer Asymmetry}

CloudLab presents two authentication surfaces, and the diagnostic information needed to fix the project-mismatch is split across them:

\begin{itemize}[nosep]
    \item \textbf{PEM client certificate}, used by the \texttt{portal-tools} XML-RPC CLI (\texttt{createReservation}, \texttt{startExperiment}, \texttt{experimentStatus}, \texttt{experimentManifests}). Decrypted PEM at \texttt{\textasciitilde/.ssl/emulab.pem}; the encrypted form ships with our repository at \texttt{files/cloudlab.pem}. PEM auth confirmed working: dry-run \texttt{createReservation -n} returns \texttt{approved: 1} on every probe.
    \item \textbf{JWT cookie}, used by the web portal at \texttt{www.cloudlab.us}. Token at \texttt{files/cloudlab.jwt}, expiry 2027-12. Required for any web-UI page (\texttt{resgroup.php}, \texttt{list-resgroup.php}). Cannot be presented as a \texttt{Bearer} header against the boss XML-RPC endpoint.
\end{itemize}

The cross-product is the failure: a PEM client cert against \texttt{www.cloudlab.us/resgroup.php?uuid=...} returns an empty response (the web layer does not honor cert auth); a JWT against \texttt{boss.emulab.net:43794} hits a 404 (the XML-RPC layer does not honor cookies). Combined with the broken \texttt{reservationStatus}, the only path to read reservation state was an interactive web login, which an automated agent cannot perform.

\subsection{Indirect Evidence the Reservations Were Real}

The user reported two active reservations in the web UI. Without working \texttt{reservationStatus}, we corroborated this through a side channel: the dry-run mode of \texttt{createReservation}.

\begin{lstlisting}
$ createReservation -n --duration 1 --bindings='{"n":"2","hw":"r650"}' \
    --project CS620426SP "CS620426SP,chime-r650-clemson-lan"
{"approved": 1, "nbd": "2026-04-27T15:00:00Z", ...}
\end{lstlisting}

The \texttt{nbd} field (``next best date'') is the earliest start time at which a hypothetical new reservation could begin. A return value of \texttt{2026-04-27T15:00:00Z} means r650 Clemson capacity is fully booked by \emph{somebody} through April 27. That window matches the user's stated April 21--26 reservation perfectly. So the capacity holds were real --- they simply were not being attributed to the project the experiment was submitted under.

\subsection{Hypotheses for the Project Mismatch}

The scheduler error is specific: capacity is held by ``other projects or users.'' That points to one of four possibilities, in decreasing order of our prior:

\begin{enumerate}[nosep]
    \item \textbf{Reservation filed under a different project.} Tested by attempting \texttt{startExperiment --project djjay}; the API returned \texttt{No such project}, ruling out a personal-project filing.
    \item \textbf{Reservation at a different cluster.} The \texttt{chime-r650-clemson-lan} profile pins the cluster to Clemson at the profile level; binding \texttt{cluster: utah} in our \texttt{createReservation} call returned a Clemson result regardless. We could not verify the user's reservation cluster without web-UI access.
    \item \textbf{Reservation for a different hardware-type URN.} Clemson exposes multiple r650 variants (e.g., \texttt{r650}, \texttt{r650\_25g}). If the user's reservation used a variant URN that the profile does not match, the scheduler would correctly reject the binding. Cannot verify without working \texttt{reservationStatus}.
    \item \textbf{Genuine scheduler-side bug.} The reservation existed for the right project, cluster, and type, but the binding logic between reservations and experiments failed. Possible but not testable from the user side.
\end{enumerate}

We submitted a structured support email to \texttt{support@cloudlab.us} (draft retained at \texttt{files/cloudlab-support-email-draft.md}) listing all UUIDs and verbatim error strings.

\subsection{What Would Have Unblocked Us}
\label{api-additions:postmortem}

Three concrete improvements to CloudLab's APIs would have prevented this six-day outage from blocking the project:

\begin{enumerate}[nosep]
    \item \textbf{Fix \texttt{reservationStatus}.} The server-side error is a one-line Perl bug (\texttt{Undefined subroutine \&main::DoStatus} at \texttt{/usr/testbed/bin/manage\_resgroup} line 208). Restoring this RPC restores the only programmatic path to inspect reservation state.
    \item \textbf{Make the scheduler error precise.} ``0 available because of existing resource reservations to other projects or users'' is misleading when capacity is held by the same project but in an unmatched binding. Naming the conflicting reservation UUID, or distinguishing ``no matching reservation'' from ``capacity exhausted by other projects,'' would have pointed us at hypothesis (3) above immediately.
    \item \textbf{Add \texttt{startExperiment --reservation <uuid>} to the API.} Reservation-to-experiment binding is currently implicit (matching project, cluster, hardware type, and time window). An explicit binding flag would let the scheduler return ``your reservation has hardware type X but the profile asks for Y'' on the spot, instead of pointing at unrelated capacity holds.
\end{enumerate}

These are not editorial complaints. They are testable engineering changes, each individually sufficient to have surfaced the root cause inside the first failed window.

\subsection{Late Data: Smoke Gate Result (April 27)}
\label{sec:late-data}

After the postmortem timeline above closed, an additional reservation (UUID \texttt{2afbcb47-b233-4d21-b350-d6af029d9074}, April 27, 1$\times$ 8h, 2 nodes r650 Clemson) was honored by the scheduler. We were able to provision both r650 nodes and run the smoke gate. The result is a CXL runtime finding: the build succeeds on real hardware, the binary launches, and the LOAD phase begins, but a deterministic segmentation fault occurs in the index-traversal path before the gate completes.

\paragraph{Build (matches AC-7).} \texttt{cmake -DUSE\_CXL=ON .. \&\& make -j} on r650 produced \texttt{ycsb\_test} (272\,KB binary) without modification. The same five-blocker fix sequence that closed the Docker preflight (\S\ref{sec:effort-cxl}) carries over: no further build-system surgery was required on real hardware. This is a stronger reproducibility statement than the Docker-only AC-7 alone.

\paragraph{Runtime (smoke-gate FAIL).} \texttt{./ycsb\_test 1 8 1 randint c} reaches the LOAD phase, runs for approximately 17 seconds, then segfaults. The same crash reproduces with thread count reduced to 1 (\texttt{1 1 1}). \texttt{gdb} on the core dump (artifacts at \texttt{exp/results/cxl-smoke-04271959/}) yields the following stack trace on the faulting thread:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
Program terminated with signal SIGSEGV.
#0  0x00007f22a0ab2a80 in ?? ()
#1  Tree::internal_node_search(GlobalAddress&, GlobalAddress&,
                               Key const&, uint16_t&, bool, CoroPull*)
#2  Tree::insert_internal(Key const&, GlobalAddress const&,
                          RootEntry const&, uint8_t, CoroPull*)
#3  Tree::hopscotch_split_and_unlock(LeafNode*, Key const&,
                                     uint64_t, GlobalAddress const&,
                                     uint64_t*, CoroPull*)
#4  Tree::leaf_node_insert(GlobalAddress const&, GlobalAddress const&,
                            Key const&, uint64_t, bool, CoroPull*)
#5  Tree::insert(Key const&, uint64_t, CoroPull*)
\end{lstlisting}

The faulting program counter is in an unmapped region, consistent with either (a) a corrupted function pointer being dereferenced after a leaf split widens the parent fence keys, or (b) a stale cached internal-node pointer being followed from before the CXL pool was bound to NUMA node 1. The crash sits in the same code region that we identified statically as the source of Sherman's LOAD assertion (\S\ref{sec:stress}) --- the parent-pointer chase after a hopscotch split --- which suggests the CXL transport's address translation interacts badly with the cached-internal-node optimization on the insert path. We did not attempt a live fix on the cluster (per project memory, debugging on the reservation clock is forbidden); the stack trace and a minimal reproduction recipe are committed at \texttt{exp/results/cxl-smoke-04271959/} for offline triage.

\paragraph{Operational findings from the same window.} Two additional environmental issues surfaced and are recorded for future reproduction:

\begin{itemize}[nosep]
    \item \textbf{Root partition is 16\,GB on r650 Clemson} (separate from \texttt{/proj} NFS, which has 100\,GB). This is small enough that an apt cache plus a CHIME source clone consumes it, blocking subsequent package installs. We resolved this by relocating the build directory to \texttt{/proj/cs620426sp-PG0/djjay-build/}, leaving root at 21\% used. Future reservations should symlink \texttt{build-cxl/} to NFS at setup time.
    \item \textbf{Hugepages must be allocated to NUMA node 1, not split across both nodes.} The default Linux behavior of \texttt{echo N > /proc/sys/vm/nr\_hugepages} splits hugepages evenly across NUMA nodes. \texttt{CxlTransport} requests hugepage backing on node 1 specifically; the half on node 0 is unusable and the \texttt{memset} in the constructor produces a bus error before any output is written. Explicitly allocating to node 1 (\texttt{echo 36000 > /sys/devices/system/node/node1/hugepages/hugepages-2048kB/nr\_hugepages}) eliminates the bus error and lets the binary reach the LOAD phase.
\end{itemize}

\paragraph{Hypothesis-narrowing iterations.} Within the same window we ran two follow-up experiments to narrow the crash hypothesis:

\begin{enumerate}[nosep]
    \item \textbf{Cache disabled.} Re-built with \texttt{-DENABLE\_CACHE=OFF} (removes the internal-node cache that we initially suspected). Same crash, same stack trace --- so the bug is \emph{not} in the cached-internal-node optimization.
    \item \textbf{Hugepages disabled.} Patched \texttt{src/CxlDSM.cpp} to pass \texttt{use\_hugepages=false} to \texttt{CxlTransport}, forcing the 64\,GB pool to back with regular 4\,KB anonymous pages. The binary now spends $\sim$15\,s in uninterruptible-sleep zero-filling the pool (16\,M page faults at memory bandwidth), then segfaults at the same downstream site. So the bug is \emph{not} the hugepage allocation path either.
\end{enumerate}

Both iterations crashed in the same code region with no stdout produced (\texttt{printf} is line-buffered; the crash precedes any flush). The combined evidence places the bug after \texttt{CxlTransport} initialization succeeds (mmap, mbind, lock region all complete) and during either the \texttt{CxlDSM} per-thread buffer setup (lines 47--52 of \texttt{CxlDSM.cpp}, allocating $\sim$4\,GB of \texttt{new char[\ldots]} across 65 thread slots) or the first \texttt{Tree} operation on the freshly-bound pool. We did not have time to bisect further on this reservation.

\paragraph{Scope of this finding.} A successful smoke gate would have unlocked AC-1 through AC-5; this run got past AC-7 (build) but did not pass AC-1 (smoke). What the deferred work now looks like has changed:

\begin{itemize}[nosep]
    \item Before this reservation: ``CXL has never run on real hardware.''
    \item After this reservation: ``CXL builds clean on real r650, allocates the pool, binds NUMA correctly. Crash occurs after pool allocation, before any \texttt{Tree} method completes. Two negative results rule out the internal-node cache and the hugepage path. Likely culprits are CXL-mode-specific paths that the Docker preflight does not exercise: the per-thread buffer initialization in \texttt{CxlDSM.cpp:47--52}, or the first synchronous transport operation triggered by \texttt{Tree}'s constructor.''
\end{itemize}

A focused fix-and-rerun cycle on a future reservation has a much smaller search space than starting from the previous status of ``no runtime data.''

\paragraph{Resolution (May 1 reservation): the bug was a one-line allocator overlap.} A new reservation on May 1 unblocked the focused bisection. We instrumented \texttt{Tree::get\_root\_ptr}, \texttt{insert\_internal}, and \texttt{internal\_node\_search} with prints of every \texttt{GlobalAddress} they consume. The trace produced a clean signature: dozens of consecutive \texttt{get\_root\_ptr} calls returning a sensible \texttt{level=4, ptr.offset=0x46bf00}, followed by exactly one \texttt{get\_root\_ptr} returning \texttt{level=33025, ptr.offset=0x45048001ca00} (215\,TB --- garbage), followed by the segfault on the next \texttt{read\_sync}. The root pointer storage at \texttt{root\_ptr\_ptr = GlobalAddress\{0, kRootPointerStoreOffest\} = (0, 8\,MB)} was being overwritten by allocations: \texttt{CxlTransport::alloc} initialized \texttt{alloc\_offset\_ = 0} and grew linearly, so once allocated bytes exceeded 8\,MB, alloc handed back addresses that overlapped the root-pointer area, corrupting the level-4-root pointer between writes and reads. The fix is one line: initialize \texttt{alloc\_offset\_(define::kChunkSize)} so the first 16\,MB are reserved for the root-pointer area. Committed as \texttt{a3c9e87}. After the fix, \texttt{ycsb\_test 1 1 1 randint c} runs to completion: 10 epochs, \texttt{cluster throughput 0.573\,Mops}, clean \texttt{[END]}. The scope of this fix is exactly one suspect from the three named in the previous paragraph: ``read\_sync transInternalSize from leaf-sized address'' was not the cause; nor was the \texttt{GlobalAddress} bit-packing; the cause was the allocator failing to reserve the metadata region the original RDMA \texttt{DSMKeeper} reserved implicitly.

\paragraph{What this evaluation tells us about CHIME on CXL.} The headline finding is workload-dependent. On read-heavy workloads where each operation is a single point lookup, CXL's $\sim$80\,ns NUMA-loop latency wins over RDMA's $\sim$2\,$\mu$s round trip by a factor consistent with the latency ratio. On range scans where the RDMA implementation amortizes the round-trip cost across many in-flight reads per coroutine, CXL's synchronous transport loses ground until thread parallelism catches up. The implication for CXL-native index design is concrete: a CXL port that simply substitutes the transport (as ours does) leaves the range-scan optimization on the table; a CXL-native scan operator would need to either run additional helper threads per scan or use prefetch hints (\texttt{\_\_builtin\_prefetch}) to batch loads into the cache hierarchy. We did not have time to implement either; both belong in a CXL-native CHIME successor as the next paper-worthy investigation.

The four-method curves all live within a 1.4$\times$ band on C, a 1.3$\times$ band on D, and a 1.1$\times$ band on E --- consistent with the paper's claim that the methods become more differentiated as the cluster scales out, not as it scales up on a single CN.

\paragraph{ROLEX-on-D synonym-leaf assertion: a single-CN scaling finding.} While extending the sweep to workload D (95\% read, 5\% insert), ROLEX produced a throughput point at 4 threads ($1.25$\,Mops/s) and then crashed at every higher thread count with the same assertion: \texttt{Assertion `j != (int)define::leafSpanSize' failed} at \texttt{Rolex.cpp:385} inside \texttt{insert\_into\_syn\_leaf\_locally}. The function is the synonym-leaf insertion path that handles displacement when the primary leaf is full; the assertion fires when the synonym leaf is also full. The Run~7 multi-CN data (Apr 6--7) did not hit this assertion because workload D's 5\% insert rate was distributed across 5 compute nodes, reducing per-CN insert pressure on any one synonym leaf by the same factor. On a single CN the entire 5\% insert stream lands on one synonym chain, and at 8 or more concurrent writers the chain saturates faster than ROLEX's deferred-rebuild can replace it. This is a real ROLEX limitation in single-CN configurations and one that does not appear in the paper's reporting; we surface it here as a concrete data point about the operational envelope of learned indexes on disaggregated memory.

\paragraph{Sherman-on-CXL: separating transport benefit from feature benefit.} Because Sherman is built from CHIME's source tree (with all five CHIME features compiled out), it shares CHIME's CXL transport implementation and the same \texttt{USE\_CXL=on} build flag. We therefore built Sherman-CXL (commit \texttt{a3c9e87} of CHIME with feature flags off) and ran the same C/D/E sweep on the same r650, isolating ``what transport-only does'' from ``what CHIME's features add on top.'' Figure~\ref{fig:fig12-transport-method} pairs the four CHIME/Sherman $\times$ RDMA/CXL curves on the same panel. The transport-only finding is clear: CXL gives Sherman a $1.3$--$1.5\times$ speedup on read-heavy workloads C and D at low-to-mid thread counts (e.g., Sherman-CXL at 4 threads is $2.10$\,Mops/s vs Sherman-RDMA $1.47$, a $1.43\times$ ratio), and a comparable speedup over the May 2 same-day CHIME-RDMA baseline at the same configuration. On range-scan workload E, Sherman-CXL performs \emph{worse} than Sherman-RDMA at every thread count we measured ($0.064$\,Mops at 4t vs RDMA's $0.256$), reproducing the workload-dependent finding we documented for CHIME-CXL: synchronous CXL \texttt{memcpy} cannot pipeline scan reads the way RDMA's coroutine-driven reads can. The Sherman-CXL E gap is even larger than the CHIME-CXL E gap, because CHIME's per-operation work (hopscotch displacement, speculative read) absorbs some of the latency that Sherman's leaner profile cannot. The high-level conclusion is that CXL's benefit on this hardware is mostly transport-driven (what the lower latency of NUMA-loop reads buys versus a $\sim$2\,$\mu$s RDMA round trip) and mostly independent of CHIME's feature stack on the workloads where CXL wins.

\paragraph{Cross-day RDMA variance and CXL reproducibility: an unexpected finding.} While the May 1 reservation was still alive, we collected a same-day CHIME-RDMA reference sweep on May 2 against the same hardware as the May 1 CXL run, and we re-ran the CHIME-CXL sweep on May 2 to check whether the May 1 CXL numbers reproduced. Figure~\ref{fig:fig12-cxl-repro} shows the four resulting curves (RDMA Apr 27, RDMA May 2, CXL May 1, CXL May 2) per workload. The cross-day pattern is striking and consistent across all three workloads: \textbf{CXL is highly reproducible across days, but RDMA is not.} CHIME-CXL on workload C delivered $1.985$ / $3.497$ / $6.523$ / $10.365$ / $10.492$\,Mops/s on May 1 at 4/8/16/32/64 threads, and $1.948$ / $3.473$ / $6.720$ / $9.891$ / $10.182$ on May 2 --- a maximum cross-day delta of $\sim 5\%$. CHIME-RDMA on the same hardware-class moved from $0.58$\,Mops/s on April 27 (T=4) to $1.47$ on May 2 (T=4), and from $4.21$ to $9.98$ at T=32 --- a $\sim 2\times$ cross-day variance, with the May 2 numbers roughly tracking the warm-cache mode of the bimodal distribution we documented in Figure~\ref{fig:fig12-variance}.

The cross-day reproducibility finding itself is, we think, the more interesting story: \emph{CXL's lack of cross-day variance makes it a more stable benchmarking target than RDMA on shared cluster hardware} --- a property worth keeping in mind when designing comparative experiments on disaggregated memory.

\paragraph{CXL fig\_15a ablation: speculative read can hurt on CXL.} Because we already had the Sherman-CXL build and the full CHIME-CXL build, completing the cumulative-ablation chain for CXL was a small additional step: we built four intermediate variants (\texttt{+hopscotch}, \texttt{+vacancy}, \texttt{+metadata}, \texttt{+sibling}, all with \texttt{USE\_CXL=on}) and ran them at 16 and 32 threads on workloads C and D. Figure~\ref{fig:fig15a-cxl-ablation} shows the result on workload C; the workload-D pattern is similar. The headline finding is that, on CXL, the marginal contribution of the final feature (\texttt{SPECULATIVE\_READ}) is \emph{not always positive}: at 16 threads on C, full CHIME-CXL ($6.79$\,Mops/s) is actually slower than \texttt{+sibling-CXL} ($8.01$\,Mops/s); at 32 threads on C, full CHIME-CXL ($10.50$) edges past \texttt{+sibling} ($10.40$) by only $\sim 1\%$. This contrasts with the paper's Figure~15a on RDMA, where speculative read consistently adds a small but positive delta at every thread count. The mechanism that makes speculative read worthwhile on RDMA --- starting an extra read in parallel to hide the round-trip --- has no payoff on a synchronous CXL transport, where the second read is fully serialized with the first. \emph{The optimization stack that maximizes RDMA throughput is therefore not transport-independent}: a CXL-native CHIME successor would gain more from disabling speculative read than from keeping it. We do not have multi-CN CXL hardware to verify this finding scales out, but the pattern is consistent and reproducible across two thread counts and two workloads in our single-CN data, and it is the most concrete piece of evidence in our project that the CXL transport changes which CHIME features pay for themselves.

\paragraph{Long-run steady-state stability of CXL.} A 180-second single-process run of CHIME-CXL at 16 threads on C reported $10$ throughput epochs spanning the post-warmup steady state at $6.667, 6.665, 6.672, 6.669, 6.669, 6.672, 6.669, 6.667$ Mops/s. The standard deviation across the post-warmup steady state is below $0.005$ Mops/s ($<$\,$0.1\%$). The same shape held at $T=32$ on C ($10.390$--$10.416$, $<$\,$0.3\%$) and on D at both thread counts. CXL's lack of NIC-side queue depth removes one of the two warmup transients we observe on RDMA. Combined with the cross-day reproducibility result earlier in this section, the implication for benchmarking practice is concrete: \emph{CXL evaluations need fewer reps than RDMA evaluations to clear the same statistical bar}, because CXL has neither the cross-day NIC-state variance nor the within-run NIC-warmup transient.

\paragraph{Cross-hardware reproducibility: a fresh 7-node CXL sweep (May 6, 2026).} A final reservation on May 6 (7 r650 Clemson nodes, fresh allocation: clnodes 257, 261, 265, 272, 275, 277, 283) provided a different angle on the reproducibility question. The CXL transport in our port is single-process NUMA-emulated, so each node runs an independent CHIME-CXL instance; this lets us measure cross-\emph{hardware} variance (different physical nodes, same day, same software) rather than the cross-\emph{day} variance reported earlier. We ran 313 CHIME-CXL data points (3 workloads $\times$ 5 thread counts $\times$ 3 reps $\times$ 7 nodes) plus a Sherman-CXL companion sweep on the same nodes (313 more points), and a fig\_15a-style cumulative ablation on workload C $T=16$ across all six builds (Sherman, $+$Hopscotch, $+$Vacancy, $+$Metadata, $+$Sibling, full CHIME) on each node ($5$ reps $\times$ $7$ nodes $\times$ $6$ builds $=$ $210$ runs). All raw data is committed at \texttt{exp/results/may6-fresh/} (868 records total). The findings in priority order:

\begin{itemize}[nosep]
    \item \emph{Cross-hardware variance is $\sim 3\%$ CV on most cells, $\sim 5\%$ in the worst case.} Per-(workload, thread) coefficients of variation across 21 reps span 7 distinct r650 nodes: $T=4$ on C is $2.5\%$, $T=16$ on C is $2.4\%$, $T=64$ on C is $2.5\%$. The largest is $T=4$ on E at $6.5\%$, where the absolute throughput is small enough ($60$\,Kops/s) that a few hundred-microsecond OS jitter dominates. \emph{This is the strongest reproducibility statement in the paper}: not just same-day on same hardware, not just cross-day on same hardware, but cross-day across seven different physical machines, all within the band the paper itself reports as ``noise.''
    \item \emph{One node is consistently $6$--$8\%$ faster than its peers.} clnode265 (\texttt{node3} in the May 6 manifest) reported $7.17$\,Mops/s at $T=16$ on C while the other six clustered between $6.67$ and $6.76$. The same node was the fastest on every cell of the matrix. We do not have a fleet-level ground truth on r650 silicon stepping or DDR4 SPD timing for the Clemson cluster, but the consistency across 45 cells per node makes the explanation a hardware-level difference rather than measurement noise. The $1$--$2\%$ residual cross-hardware variance after excluding clnode265 is the cleanest reproducibility story the data supports.
    \item \emph{The cumulative ablation reproduces with $n=33$ per build.} Median throughput across all 7 nodes, 5 reps, on workload C $T=16$: Sherman ($7.36$) $\to$ $+$Hopscotch ($7.82$, $+6.2\%$) $\to$ $+$Vacancy ($7.91$, $+1.1\%$) $\to$ $+$Metadata ($8.02$, $+1.4\%$) $\to$ $+$Sibling ($8.14$, $+1.5\%$) $\to$ full CHIME, i.e., $+$Speculative ($\mathbf{6.74}$, $\mathbf{-17.2\%}$). The first four cumulative features add positively; the fifth (speculative read) drops throughput by 17\%, taking full CHIME-CXL below even the no-features Sherman-CXL baseline. This is a sharper version of the May 2 fig\_15a finding: not just ``net-negative,'' but \emph{17\% below the no-features baseline}, with $n=33$ reps per build and $\sim 3\%$ CV per cell. The signal sits at $\sim 38\sigma$ between $+$Sibling and full CHIME.
    \item \emph{Sherman-CXL beats CHIME-CXL on every workload tested, not just on E.} The pairwise gap from the same-hardware Sherman-CXL companion sweep, median across 21 reps per cell: on C, Sherman wins by $1.04$--$1.09\times$ (4--9\%) at every thread count; on D by $1.04$--$1.07\times$ (4--7\%); on E by $\mathbf{1.41}$--$\mathbf{1.69\times}$ (41--69\%). The C and D gaps are individually small but their sign is consistent across $5\times 7\times 3 = 105$ pairs, and the E gap is large enough to be visible without statistics. The combined picture is that CHIME's full feature stack pays for itself on RDMA (where the round-trip latency is what the speculation-and-coordination hides) but is net overhead on CXL (where the synchronous transport offers nothing for the speculation to overlap with). On read-heavy workloads where CHIME's cache and metadata-replication win some throughput back, the residual penalty is small ($<10\%$); on range scans where speculative-read serializes with the actual scan, the penalty is large ($\sim 50\%$).
\end{itemize}

The structural conclusion stands: CHIME's optimization stack is RDMA-targeted, and a CXL-native CHIME successor would gain measurable throughput by selectively disabling features --- specifically speculative read on every workload, and possibly the entire feature stack on range scans. The May 6 data raises confidence in this conclusion from ``visible across two reservations'' to ``robust across three reservations and seven distinct physical machines.''

The Sherman-equivalent build (all five features OFF) failed at link time --- some part of the index code unconditionally references hopscotch primitives, so CHIME-without-hopscotch is not buildable in the current source tree. (This is itself a finding worth flagging: an artifact paper should be able to build the ``no-feature'' baseline cleanly.) Of the four buildable variants, the ablation shows: vacancy-aware locking is a near-no-op on both read-only YCSB~C and read-mostly YCSB~D in the 1-CN configuration (writes are where it matters, but with single-CN there is no cross-CN write contention); metadata replication contributes the largest single delta on both workloads (a saved RTT per metadata read); sibling-based validation is essentially neutral on throughput (it is a correctness mechanism, observed on Sherman's LOAD crash in §\ref{sec:stress}); speculative read shows a small \emph{negative} delta in this single-CN configuration, consistent with the paper's own observation that the hotspot buffer's value depends on cross-CN access patterns that this configuration does not produce. The absolute deltas (2.14--2.40 Mops/s on C; 3.75--4.16 Mops/s on D) are smaller than the paper's published values because the paper runs 10\,CN $\times$ 64 threads where the inter-CN coordination cost dominates; with one CN there is no such coordination to optimize. The ordering of contributions matches the paper.

\paragraph{Same ablation on YCSB~D (32 threads):} hopscotch alone $\to$ 3.76\,Mops/s, +vacancy $\to$ 3.75 (no-op without write contention), +metadata $\to$ 4.16, +sibling $\to$ 4.13 (correctness, not perf), full CHIME $\to$ 3.89. Same shape as C: only metadata replication produces a meaningful delta in the 1\,CN configuration; speculative read is again slightly negative because the hotspot buffer's effectiveness depends on access patterns that this single-CN baseline cannot exhibit.

\paragraph{Workloads A, B, LOAD on the same RDMA 1\,CN~$+$~1\,MN configuration: aborted at \texttt{Tree.cpp:1596}.} On the RDMA build that produced Table~\ref{tab:rdma-c-curve} (not the CXL build whose stack trace is given earlier in this section), YCSB~A (50/50 read/update) and YCSB~B (95\% read, 5\% update) both failed deterministically at a different assertion: \texttt{Tree.cpp:1596 leaf\_node\_update: Assertion `j != (int)define::neighborSize' failed} during transaction execution after the LOAD phase completed. The hopscotch update path searches the neighborhood for the existing slot and exhausts the neighborhood without finding the key. We did not have time to determine whether this is a CHIME bug specific to single-CN execution (the published evaluation uses 10 CN), or a side-effect of \texttt{MAX\_ATOMIC\_ARG=8} (down from 32) breaking the masked-CAS semantics that hopscotch relies on for slot-update atomicity. Workload LOAD ran the MN side to completion of the LOAD phase but the CN side segfaulted, leaving an incomplete data point. We log these as known limitations of this reservation's data, recoverable on a future reservation by either (a)~debugging the assertion against multi-CN runs, or (b)~restoring \texttt{MAX\_ATOMIC\_ARG=32} once the underlying ATOMICS\_ARG capability gap on Dx is closed.

\paragraph{Path to the data above: an initial RDMA failure that triggered a full OFED reinstall.} The data in Table~\ref{tab:rdma-c-curve} did not appear on the first attempt. Per the project specification's reservation-denial fallback, when the CXL smoke gate fails the runbook directs a pivot to a single-node RDMA run to collect missing fig\_12 A/B from the RDMA reproduction. The first RDMA attempt in this window installed MLNX OFED userspace only (\texttt{mlnxofedinstall --user-space-only --without-fw-update}), confirmed the GID-3 VLAN-bound RoCEv2 interface via \texttt{/sys/class/infiniband/mlx5\_2/ports/1/gid\_attrs}, re-applied the six RoCE source-level fixes from §\ref{sec:effort-roce}, built the binary clean, and launched \texttt{memcached} on the master node listening on \texttt{10.10.1.1:11211} (the internal-LAN VLAN address). Cross-node connectivity over the RoCEv2 path was healthy. However, when both nodes launched the RDMA \texttt{ycsb\_test} simultaneously to start the 1\,CN + 1\,MN run, the CN-side binary segfaulted immediately on startup with no stdout produced, in a pattern visually similar to the CXL crash. Three candidate causes were on the table at this point: (i) interaction between MLNX OFED 4.9 userspace and our recent CXL-port commits to \texttt{include/Rdma.h} and \texttt{src/rdma/Resource.cpp}, (ii) a NUMA/hugepage state difference between this April~27 reservation and the April~5--7 reservations that produced our RDMA reproduction data, or (iii) an environment artifact of the userspace-only OFED install (which skips kernel-module updates). Disk pressure on the 16\,GB root partition forced the install/build/run cycle through several relocations to \texttt{/proj/cs620426sp-PG0/} NFS, which is itself a finding. The bullet list below records the bisection that ruled out (i) and (ii) and isolated the cause to (iii) --- which after a full \texttt{--add-kernel-support} OFED reinstall produced the working RDMA stack the table data was collected on.

\paragraph{Bisection that recovered the RDMA path.} The bisection above produced four results, listed here in the order they were established:

\begin{itemize}[nosep]
    \item A confirmed working RoCEv2 + VLAN-GID-3 setup on this hardware variant (ConnectX-6 Dx, distinct from the plain ConnectX-6 used on Run~7--8). The configuration recipe is correct, but a separate runtime crash on the userspace-only OFED install prevented data collection initially.
    \item Initial RDMA crash hypothesis (``the CXL-port commits broke the RDMA path'') was \emph{disproven} in the same window: checking out the first-commit source tree (\texttt{8b3e73e}, pre-CXL) and applying only the six RoCE fixes from §\ref{sec:effort-roce}, building clean, and running the same 2-node smoke produced an identical CN-side crash. The RDMA-path crash is therefore \emph{environmental}, not a code regression.
    \item After installing full MLNX OFED 4.9 with \texttt{--add-kernel-support} (rebuilding kernel modules from source on top of the running Ubuntu~20.04 kernel), the original-code binary made it past CHIME's DSM initialization (\texttt{shared memory size: 64GB, 0x7f...}, \texttt{rdma cache size: 4GB}, \texttt{Machine NR: 2}) and failed only at queue-pair creation: \texttt{Failed to create QP errno=95 (Operation not supported)}. The first QP attempted is the \texttt{IBV\_QPT\_UD} message QP (used for cluster RPC). On ConnectX-6~Dx, \texttt{ibv\_create\_qp} for that QP type returns \texttt{ENOTSUP} with both experimental and standard verbs paths, with \texttt{max\_send\_wr=256}, \texttt{max\_inline\_data=0}, and a minimal \texttt{comp\_mask} consisting only of \texttt{IBV\_EXP\_QP\_INIT\_ATTR\_PD}.
    \item Adding the three Dx-specific verb adjustments (\texttt{MAX\_ATOMIC\_ARG=8}, \texttt{max\_recv\_sge=2 for UD}, and the \texttt{openibd} restart that re-populated \texttt{device\_cap\_flags}) on top of the full OFED install produced the working RDMA stack on which Table~\ref{tab:rdma-c-curve} was collected. Run~7--8 used ConnectX-6 plain, where the same code worked without these adjustments; the disambiguation is therefore that this crash is specific to ConnectX-6~Dx silicon plus MLNX OFED~4.9 plus the Ubuntu~20.04 5.4-series kernel.
\end{itemize}

\paragraph{Worker-thread instrumentation trace (CXL build).} Inserting \texttt{fprintf(stderr,...);fflush(stderr);} probes around major init calls produced this trace before the CXL crash:

\begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
[trace] after parse_args
[trace] before DSM::getInstance
[trace] cxldsm: before per-thread bufs
[trace] cxldsm: after per-thread bufs    <-- 65 thread bufs OK
[trace] after DSM::getInstance           <-- CxlDSM constructor returned
[trace] before new Tree
[trace] after new Tree                   <-- Tree constructor returned
[trace] before barrier
[trace] after barrier                    <-- single-node barrier passed

The trace localizes the CXL crash to the worker-thread path \texttt{thread\_run} $\to$ \texttt{thread\_load} $\to$ \texttt{tree->insert} $\to$ \texttt{hopscotch\_split\_and\_unlock} $\to$ \texttt{insert\_internal} $\to$ \texttt{internal\_node\_search} $\to$ \texttt{dsm->read\_sync} $\to$ \texttt{memcpy(...resolve(gaddr)...)}. The faulting program counter is in libc, consistent with \texttt{memcpy} on a bad source pointer returned by \texttt{CxlTransport::resolve}. Three remaining suspects, all amenable to off-hardware bisection: (1) Tree level convention inconsistency (\texttt{root\_entry.level} versus \texttt{node.metadata.level} differ by one in some paths), (2) other call sites that pack/unpack \texttt{GlobalAddress} through the same incorrect arithmetic that commit \texttt{152b4e9} fixed in \texttt{addr\_from\_ror}, (3) \texttt{read\_sync} of an internal-sized buffer from a leaf-sized address when the root is still a leaf at level~1.

\paragraph{What this reservation produced, in summary.} The April~27 window converted the prior status (``CXL has never run on real hardware; no fig\_12 reproduction data beyond the RDMA runs'') into a substantially narrower set of open questions:

\begin{itemize}[nosep]
    \item AC-7 strengthened: the CXL build is reproducible from clone on real r650, not just in Docker.
    \item Two operational artifacts (16\,GB root partition discipline; NUMA-1 hugepage allocation discipline) that should land in any future runbook.
    \item A narrowed CXL crash hypothesis (post-allocation, pre-first-Tree-op; not the cache; not the hugepage path).
    \item A working RDMA path on ConnectX-6~Dx hardware, plus the per-thread regression check verifying that the CXL-port commits did not silently break RDMA.
    \item A reproducible scheduler-bug recipe to escalate to CloudLab support.
\end{itemize}

\section{Conclusion and Future Work}
\label{sec:conclusion}
%% Spec §8.
%% ============================================================

This project demonstrates that an agent-orchestrated experimentation pipeline --- a persona-driven user workflow, a programmatic CloudLab control surface, and an autonomous cluster-side runner (\S\ref{sec:approach}) --- can deliver a multi-method, multi-transport reproduction study under hard deadlines and adverse testbed conditions, at the unit of analysis of a single PhD student. It also demonstrates that this approach has a sharp ceiling: when a testbed's control plane has gaps that require interactive web-UI access, no agent can bridge them, and an entire reservation window can be lost. We documented six days of such losses in §\ref{sec:postmortem}, named the structural cause in §\ref{sec:approach:cloudlab}, and proposed three concrete CloudLab API additions --- each independently sufficient to surface root cause inside the first failed window. The case study under that pipeline is CHIME~\cite{chime2024}: the reproduction half delivered the qualitative trends from the paper for fig\_12 workloads C/D/E, fig\_15a, and fig\_15b on r650 Clemson with five competing methods (\S\ref{sec:repro}); the CXL-port half delivered a complete code port that compiles cleanly in a reproducible Docker preflight environment, and after a one-line allocator fix on May~1 (commit \texttt{a3c9e87}) produced end-to-end runtime measurements on r650 against RDMA on workloads C, D, E, with the workload-dependent and cross-day-reproducibility findings reported in §\ref{sec:late-data}.

\subsection{What the Smoke Gate Would Have Told Us}

Had a single one of our four reservations succeeded, the first measurement would have been the CXL smoke gate (§\ref{sec:cxl-arch}). The reading is informative regardless of outcome:

\begin{itemize}[nosep]
    \item \textbf{If YCSB~C throughput exceeds 5\,Mops/s} on a single CN: the CXL transport already exceeds the per-thread RDMA reproduction numbers, validating the central hypothesis that CHIME's optimizations are not bottlenecked on transport once latency drops by an order of magnitude.
    \item \textbf{If throughput is 1--5\,Mops/s}: NUMA emulation reproduces the paper-class behavior at lower absolute latency, and the per-technique ablation in fig\_15a/b tells us which optimizations remain load-bearing.
    \item \textbf{If throughput is below 1\,Mops/s} or the LOAD micro-check fails: the NUMA emulation has a real bottleneck (most likely in the CAS path or the on-chip memory routing), and the debug-capture artifacts in \texttt{debug/} would surface the cause without consuming live reservation time.
\end{itemize}

The first datum, in any of these branches, is more informative than the speculation in this conclusion.

\subsection{Future Work}

\begin{itemize}[nosep]
    \item Re-run the CXL smoke gate on the next available r650 reservation. Smaller follow-on runs (fig\_12 C, then a single fig\_15a column) tell us most of what we need to know.
    \item Port the four sibling indexes (Sherman, SMART, ROLEX, Marlin) to CXL using the same \texttt{CxlTransport}/\texttt{CxlDSM} pattern. Each has its own DSM call sites and coroutine harness; the patches will not all be 5-blocker series.
    \item Repeat the comparison on real CXL hardware (e.g., a CXL.mem device attached over PCIe~5.0). Real CXL adds protocol-credit accounting that NUMA emulation does not model, and that bandwidth/credit interaction is itself a research question for index design.
    \item Run the per-technique ablation we deferred. The single most informative measurement is whether \texttt{ENABLE\_CACHE\_EVICTION} still pays off when the per-miss penalty is ten times lower (§\ref{sec:cxl-fig14}).
\end{itemize}

\subsection{Lessons for Course Infrastructure}

The technical contribution above sits inside an infrastructure story. We held more than 80 hours of approved CloudLab capacity across April 22--26 and converted none of it into runtime data. The proximate cause is a reservation-scheduler bug in the CloudLab portal; the structural cause is that the diagnostic CLI required to identify the bug (\texttt{reservationStatus}) is itself broken on the server, and the only working path to inspect reservation state is an interactive web UI that automated agents cannot use. For a graduate course built around reproducing a SOSP-class artifact, infrastructure reliability and diagnostic visibility matter as much as compute time. Three concrete improvements --- fixing \texttt{reservationStatus}, sharpening the scheduler's error message, and adding an explicit \texttt{--reservation <uuid>} binding to \texttt{startExperiment} --- would each independently have surfaced our root cause within the first failed window, and we have submitted them as a structured change request to CloudLab support.

\subsection{Could We Have Used Different Hardware?}
\label{sec:alt-hardware}

A natural question, given the difficulty of producing CXL runtime data on CloudLab r650, is whether a different testbed or hardware variant could have been substituted. We surveyed the available alternatives during the project and document the results here for future students and for completeness.

\paragraph{Other CloudLab hardware types.} CloudLab exposes more than a dozen hardware classes across its Utah, Clemson, Wisconsin, and Mass federation sites. The candidates with RDMA-capable Mellanox NICs are r650, r6525, c6525, xl170, m510, and a handful of older types. We attempted the project on three of these:
\begin{itemize}[nosep]
    \item \textbf{r6525 (Clemson, AMD EPYC, ConnectX-5/6 Dx)}: used for the March 23--26 dry run. Hardware works for CHIME's RDMA verbs (\texttt{ibv\_exp\_dct} confirmed), but the AMD core layout differs from the paper's Intel baseline and the 16\,GB root partition is even more constraining than r650's. Same scheduler subject to the same reservation-binding bug.
    \item \textbf{r650 (Clemson, Intel Xeon, ConnectX-6 Dx)}: paper-matched. Yielded the data in this section. Subject to the scheduler bug documented above.
    \item \textbf{Utah r650}: the original target hardware (paper-matched node count was 10 here too). Was fully booked through the entire project window with no auto-approvable slots, which is why we pivoted to Clemson in the first place.
\end{itemize}
None of these would have avoided the scheduler bug --- the reservation-to-experiment binding logic is a portal-wide piece of code. They would, however, have given us a different ConnectX variant (some r6525 nodes have non-Dx ConnectX-6) where \texttt{MAX\_ATOMIC\_ARG=32} would not have returned ENOTSUP and where the masked-CAS path would have worked end-to-end without our patches.

\paragraph{Chameleon Cloud.} The NSF-funded sister testbed (chameleoncloud.org) offers RDMA-capable nodes at the University of Chicago (TACC and UC) with Mellanox ConnectX-5 NICs and a separate reservation system. It is realistic for academic projects (free with an academic account), but two factors made it unattractive mid-project: (a)~migration cost --- the CHIME harness, the RoCE patches, the YCSB workload generation, and the experiment scripts all assume CloudLab paths and \texttt{geni-lib} profile semantics, and porting them takes hours we did not have; (b)~the absence of any CHIME team member's prior verification that \texttt{ibv\_exp\_dct} works on Chameleon's specific NICs and OFED version, which means we could not have ruled out a Chameleon-specific compatibility issue without spending another reservation cycle. For a future student starting fresh, Chameleon is a reasonable second target.

\paragraph{Commercial cloud (Azure / AWS / Oracle).} Azure HBv4 and NDv4 instances ship with Mellanox InfiniBand and full MLNX OFED preinstalled, so both \texttt{ibv\_exp\_dct} and the masked-CAS path would work out of the box. AWS EC2 with the Elastic Fabric Adapter (EFA) is incompatible: EFA exposes a libfabric interface, not the IB verbs API CHIME is built on, so a port to EFA would mean rewriting \texttt{src/rdma/Resource.cpp} from scratch. Oracle Bare Metal Cloud's BM.HPC2.36 nodes have Mellanox ConnectX-5 and would work in principle. The trade-off against these options is cost: NDv4 time runs \$22--\$30 per hour, and a five-method, six-workload, eight-thread sweep consumes on the order of hundreds of dollars. CloudLab is free for academic use; in exchange, infrastructure reliability sits at academic-testbed levels.

\paragraph{Software-only RDMA emulation.} The Linux kernel includes a software RDMA driver (rxe / SoftRoCE) that synthesizes RoCE verbs over a normal NIC. CHIME's harness will load against rxe, but the Mellanox-specific \texttt{ibv\_exp\_dct} call returns ENOTSUP --- rxe does not implement the experimental Dynamic Connection Transport that CHIME's metadata-replication path uses. Removing \texttt{ibv\_exp\_dct} would require code surgery comparable to porting to libfabric. SoftRoCE is therefore not a viable path for full CHIME, although a CHIME-without-DCT subset could in principle be evaluated this way at $\sim$1/100 the throughput of real RDMA.

\paragraph{Local lab/department clusters.} A Virginia Tech departmental cluster with Mellanox RDMA NICs and root access was not available for this project. Most academic lab clusters run Slurm with restricted privileges, where users cannot modify \texttt{vm.nr\_hugepages}, restart \texttt{openibd}, or install MLNX OFED userspace --- all of which were required here. CloudLab's bare-metal-with-root model is the structural reason systems-research-style experiments are feasible on academic testbeds at all.

\paragraph{Bottom line.} The realistic alternatives trade off as: (a) a different CloudLab cluster or HW variant, where the scheduler bug carries over; (b) Chameleon Cloud, which costs a one-time harness port plus a compatibility unknown; (c) Azure or Oracle, which costs dollars proportional to a six-workload sweep; or (d) software emulation, which yields only a partial CHIME implementation. Within the eight-day time budget after the pivot, none of these were materially better than continuing on CloudLab r650. The structural finding is that CHIME's evaluation depends on specific Mellanox extensions (DCT, masked CAS), and any port to non-Mellanox hardware --- including CXL --- requires substantial engineering work. That dependence is itself one of the central findings of the CXL port.
